# Part A: Application Setup and Security Assessment

**Application.** StudentHub, an existing Django/SQLite Student Information System by Tasmiul Alam Shopnil. Repository: https://github.com/tasmiul/student-management-system-django . Reviewed commit: `ecbffaa293753af50d93eb052ac94d87d28d0845`; MIT license retained. This work covers Part A only.

**Setup.** The desktop package includes the application source, Python 3.12.10 for Windows x64, Django 6.0.9, locked dependencies, an initialized SQLite database, a clean database snapshot, an SQL dump, and installation instructions. Missing migration source files were generated from existing models. A separate idempotent seed command repairs the upstream setup mismatch and creates fictional demonstration records. Frontend resources were bundled locally. Run `01-Start-Website.cmd`, then visit http://127.0.0.1:8000/ . Stop using `02-Stop-Website.cmd`.

**Existing functionality and data flow.** Django ORM connects to `website/db.sqlite3`. Accounts are stored separately from student profiles, contact information, addresses, courses, grades, registrations, and fees. The package contains three fictional students, three courses, published grades, tuition/payment records, and attendance. Staff can manage records; students can view their own profiles, grades/GPA and fees. Passwords are stored as Django hashes. Login, logout and basic access checks are inherited upstream features. The faculty demo account uses the existing staff flag; independent faculty permissions are incomplete, so this is not a completed fine-grained RBAC implementation.

**Security findings.** All demonstrations used disposable synthetic data in temporary databases and media directories, never real records or third-party systems.

| Finding | Evidence and risk | CIA impact |
|---|---|---|
| Private documents have a public download path | The document list filters `is_public`, but `/media/` serves files without checking document permissions. An anonymous request returned HTTP 200 with the exact contents of a synthetic private file. Knowledge of its URL is required. Source: `documents/views.py:14–20`, `sims/urls.py:41–42`. | Confidentiality: private student documents could be disclosed. |
| GET requests modify student status | With CSRF enforcement enabled, a tokenless POST was denied with 403, while a tokenless authenticated GET changed a student's status from active to suspended. Source: `students/views.py:197–208`. | Integrity: authenticated users may trigger unintended changes by following links. The test did not show account lockout or service disruption. |
| Expired registration windows are not checked at the action endpoint | An expired offering was absent from the student list, but its registration URL created a PENDING request. Source: `registration/views.py:27–29,58–71`. | Integrity: application deadlines can be bypassed. This did not automatically approve enrollment. |

**Additional observations.** Six failed logins were rejected, and a subsequent correct login still succeeded; no lockout was observed within that bounded test. Uncontrolled password guessing could threaten confidentiality/integrity and consume password-hashing resources, but no compromise or availability failure was demonstrated. Source review also identified development configuration defaults and potential spreadsheet formula interpretation in CSV exports. Detailed evidence, limitations and source references are provided in `docs/Part-A-Security-Assessment.md` and `evidence/security-assessment.json`.

**Verification.** The package's functional checks exercise login/logout, staff and student pages, access denials, student create/edit/delete, grade/payment persistence, CSV export, seed idempotence, and SQL restoration on a temporary copy. See `evidence/functional-checks.json`. Browser screenshots in `evidence/` show the actual local application. No Parts B–E security implementation is claimed; these findings remain part of the baseline assessment.
